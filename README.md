# ClaudeRunway

Local-compute token savings for Claude Code.

Two independent pieces, both built on the same idea: push work onto local compute (a local vector DB, a local LLM) instead of Claude's own context, so Claude only pays tokens for a distilled result rather than raw data.

1. **Qdrant codebase memory** — per-project semantic memory over code/docs, so Claude can retrieve relevant chunks instead of grepping and reading whole files, and store any text in that same collection for `qdrant-find` to return later.
2. **Local compression (LM Studio)** — a local model summarizes large, mechanical content (logs, build output, big diffs) server-side before anything reaches Claude's context.

Each piece works independently — you don't need LM Studio to use the Qdrant memory, or vice versa.

## Known limitations

- Claude Code doesn't render MCP progress notifications visibly in the UI, though `index_repo`/`sync_repo` still report progress internally to avoid call timeouts on large repos.
- `codebase-indexer` and the `qdrant` server (`qdrant-find`/`qdrant-store` and the compact tools) are independent MCP servers that both need to agree on `QDRANT_URL`/`COLLECTION_NAME`/`EMBEDDING_MODEL`. `setup_project.py init` writes the same value into the `qdrant` and `codebase-indexer` blocks; a hand edit has to change each one. `memory-bank`'s `EMBEDDING_MODEL` is deliberately separate (see below).
- Compression is lossy by nature — don't use the compress tools on source code you intend to edit, or on output you need verbatim (something to parse, a diff to apply, an exact string to grep for next). `compress_text` only saves tokens for content you already legitimately hold (e.g. your own draft); for files and commands use `compress_file`/`compress_command_output`, which read the source server-side.
- **The savings tracker (`/my-savings`) is an online observation, not a benchmark.** It reports exact characters before and after compression and the percent reduction (exact for newly recorded history; rows from before schema v6, and v6 rows rebuilt from token estimates, are approximate or left out), but it observes the counterfactual online rather than measuring it via a controlled A/B run (that's what `EVALUATION.md`'s tracks are for — see Track D). The only token figure is the opt-in per-model one, which is derived (characters saved ÷ that session's own observed chars-per-token, counted once per request that carried the result), labelled as derived, and still not a measurement. Treat what the content would have cost in tokens as unknown beyond that.
- **`CLAUDE_RUNWAY_TRACK_SAVINGS` needs setting in two places, not one** (`.mcp.json` for the MCP server, a shell export for the hooks, which have no `env` field). See [Environment variables](docs/environment-variables.md) and [Savings tracker](docs/savings-tracker.md).
- `focus` on `compress_file`/`compress_command_output`/`fetch_url` handles positional asks ("the lead section," "the first N lines") automatically, with two residual limits: the heading-detection heuristic only helps for content with clear heading structure (plain text such as a log falls back to a fixed ~4000-char guess), and `_looks_positional` is a strict whole-phrase match against a fixed list, so a positional phrasing outside it falls through to the position-aware classifier, which isn't fully reliable on its own. See `libs/local_compress_lib.py`'s docstrings.
- **Chunks are cut to the embedding model's token window, and every file is indexed in full with no cap.** The model embeds only the first N tokens of a text (read from the loaded model; for the default model that is 128 or 256 depending on the FastEmbed version and model snapshot installed, which is why it is read rather than assumed), so the indexer cuts each chunk to fit and reads `EMBEDDING_MODEL`'s own limit rather than assuming one. The cost lands on the caller: chunk count is several times what line-based chunking produced, indexing is slower, collections are bigger, and a minified bundle or data dump can become thousands of chunks (a run of non-whitespace longer than the tokenizer's per-word limit is one unknown token, so such a chunk can be long in characters). There is deliberately no per-file chunk cap and no skip threshold. `index_repo`/`sync_repo` report a running count while hashing, then progress per file, and name the files that produced the most chunks, `ingest_to_qdrant.py` prints each file's count, and `preview_index` shows it beforehand; exclude files you do not need searched with `INDEX_EXCLUDE_DIRS`/`INDEX_INCLUDE_EXTENSIONS`. `overlap` is now in tokens, `chunk_lines` is accepted but ignored, and chunk metadata is `file_path` + `line_number` + `char_range` (points indexed earlier keep `line_range` until re-indexed; readers accept both). If the window cannot be read from the model, indexing stops with an error instead of guessing. See "How files are chunked" in [Installation](docs/installation.md).
- **An index built by an older release is rebuilt by the first `sync_repo` after updating.** The sync manifest is versioned and an old-format one is ignored, so that sync re-chunks and re-embeds every file in one long call (`upgrade` offers to remove the stale manifest). It first reports points in the collection that are not indexer chunks, which can be deleted with a re-indexed file's old chunks, and afterwards removes chunks of files no longer on disk. `index_repo` writes the manifest too when it starts from a clean slate (`reset=true`, or a collection that was absent or empty), so a `sync_repo` after it picks up from there; a `force=true` run into a collection that already holds points writes none, and neither does a run into any collection other than this project's own (the manifest is one file per checkout and does not record which collection it describes). `ingest_to_qdrant.py` writes none unless you pass `--write-manifest`: the CLI reads its settings from the shell, not `.mcp.json`, so it cannot tell which collection `sync_repo` uses for this checkout, and the flag is you saying that `--collection` (on `--qdrant-url`) is that one. With it the CLI follows the same rules as `index_repo` (written only with `--reset` or into a collection that was absent or empty, never on `--dry-run` or after a failed run, old manifest removed before anything is deleted or stored); without it the first `sync_repo` after a CLI index re-embeds every file a second time. A file that is still on disk but outside the rebuild's scope (a different `scope`, extensions, excluded directories or gitignore setting) keeps its old chunks and is recorded in the manifest as kept, apart from the file hashes. Every later `sync_repo` checks whether such a file has been deleted and removes its chunks if so, and re-indexes it once a scan includes it; a file whose existence cannot be checked is left alone.
- **`qdrant-find` returns 10 hits unless you pass `limit`.** Repetitive content (generated clients, JSON fixtures, lock files) can fill the top 10 with near-duplicates and push the chunk you want past it: raise `limit`, narrow the query, or fall back to Grep on a local checkout or `find_in_collection` with a higher `limit`. A hit with `line_range` in its metadata comes from an index that predates token-window chunking, where most of each chunk could not be matched at all, so a miss there is not proof the code is absent.
- **The shared `memory-bank` collection locks in whichever `EMBEDDING_MODEL` created it first** — every project's memory-bank server writes into the SAME collection and Qdrant's named-vector schema is fixed at creation. A project with a different model gets a clear mismatch error, but every project sharing the collection must agree on one value. That value is the `memory-bank` block's own `EMBEDDING_MODEL`, set independently of the code-index model: `init --embedding-model` never touches it, and `init --memory-bank-embedding-model` changes it (with a warning).
- **Changing `EMBEDDING_MODEL` after a collection has data requires manually dropping the collection (directly in Qdrant) and re-indexing** — old and new vectors aren't compatible. Change it deliberately with `init --embedding-model <model>` (which warns; a plain `init` re-run never changes it). `index_repo(reset=True)` cannot do the rebuild itself: it always does a filtered delete that preserves `metadata.source == "memory-bank"` points. If you call `sync_repo` against a dropped collection it returns an explicit error; follow it with `index_repo`.
- **A server-side "auto mode classifier" — separate from anything in `.claude/settings.json` — can block `/my-gh-autowork`'s orchestrator `Agent` call outright**, contradicting the skill's "Zero required human touchpoints" claim in some environments. Confirmed live on 2026-09-19: rejected before the subagent ran a tool call, and a follow-up self-correction via `.claude/settings.json` was separately blocked as `[Self-Modification]`. **Confirmed workaround, causation NOT confirmed:** adding the narrow `Bash(git fetch *)`/`Bash(git push *)`/`Bash(gh pr *)`/`Bash(gh api *)` rules let the identical call succeed on retry. **Never broaden this to a wildcard like `Bash(git:*)`/`Bash(gh:*)`/`Bash(uv:*)`** — each is an arbitrary-command-execution bypass (`git -c alias.x='!<shell command>' x` runs arbitrary shell via git's alias mechanism; `uv run <script>` executes arbitrary code by design). **Narrow is not the same as safe**: even the confirmed rules still permit code execution through legitimate flags (e.g. `git fetch --upload-pack=<cmd>`). See [Installation](docs/installation.md)'s "If you plan to run `/my-gh-autowork`" paragraph.
- **`sync_repo`/`index_repo`/`ingest_to_qdrant.py` retry on a dropped Qdrant connection** (`libs/qdrant_retry.py`). On macOS, Docker Desktop's `vpnkit` can silently close an idle pooled connection while the local embedding model loads, surfacing as `httpx.RemoteProtocolError`/`ConnectError`; no Qdrant-side config helps. Raising Docker Desktop's `vpnKitMaxPortIdleTime` (default 300s, `0` disables culling) only reduces how often it happens.
- **LM Studio serves a limited number of requests in parallel (default 4) and queues the rest**, so heavy concurrency (parallel subagents, `/my-gh-autowork`) can push a compression request past the 60s timeout, and that output then reaches Claude uncompressed. It is reported as a timeout, not an outage. See [LM Studio concurrency and the timeout](docs/environment-variables.md#lm-studio-concurrency-and-the-timeout).

It imports no client SDK: the caller builds the model client and passes it to `compress()`, and a timed-out request is reported through the library's own `CompletionTimeout`. Used by both `compress_mcp_server.py` and `hooks/compress_output.py` — keeps them from drifting apart. |

Still a draft — design notes and open questions are in the file's docstring. |

Separate from `local-compress` so a project that never looks at savings or metrics does not carry those five tools' schemas. Recording does not need it (the `local-compress` server and the hooks write savings events regardless); without the block the tools do not exist, which is an unknown-tool error, not empty data. |
| `libs/savings_ledger.py`          | Shared, dependency-light storage + formatting for the opt-in savings tracker (see [Savings tracker](docs/savings-tracker.md)). | `libs/session_id_lib.py`          | Shared module classifying every way this toolkit's MCP-server/hook code can get or approximate a `session_id`, behind one `session_id(strategy, ...)` entry point with four strategies (`HOOK_PAYLOAD`, `SHADOW_FILE`, `TRANSCRIPT_SCAN`, `PROXY`) — see the module's own docstring for the full decision table. `SHADOW_FILE` is kept populated by `hooks/record_session_id.py` below, deliberately independent of `libs/savings_ledger.py` (same sessions directory convention, no code dependency). |
| `libs/metrics_lib.py`             | Shared, generic cross-tool metrics store (see [Shared metrics store](docs/metrics.md)) — a `MetricsStore` class over ONE SQLite table (`~/.claude/claude-runway/metrics.db`) any domain can write append-only events into via `record`/`increment`/`decrement`, aggregated via `summary`/`by_event_type`/`trend`. Current writers: `my-gh-autowork`'s per-run outcomes (`metric_id="autowork"`) and memory-bank's per-call `recall`/`remember`/`forget` counters (`metric_id="memory-bank"`, via `memory_events_lib.py`). `savings.db` and memory-bank's detailed per-point `memory-events.db` log stay where they are. |

| `templates/settings.json.template` | Two tiers of hook config: a CORE `SessionStart`/`SessionEnd` pair (always included, only `--skip-hooks` omits it) registering `hooks/record_session_id.py` below; and an optional, local-compress-gated `PostToolUse` block that compresses tool output over a size threshold — by size, not by a hardcoded list of commands, apart from the byte-exact Bash exemptions in [Skills and hooks](docs/skills-and-hooks.md#exactness-critical-commands-bash-only). | `hooks/compress_output.py`   | Formerly `compress_bash_output.py` (renamed; `upgrade` migrates existing settings). The hook script referenced by `templates/settings.json.template` at its path in the tools repo (nothing copied into the target project). Filename is legacy -- fires on Bash, Grep, Glob, WebFetch, and WebSearch, plus `mcp__local-compress__.*`, the `qdrant` server's conversation-compact tools (`compact_store`/`compact_find`/`compact_prune`, never `qdrant-find`/`qdrant-store`) and a vetted GitHub MCP allowlist (see [Skills and hooks](docs/skills-and-hooks.md) for the full matcher and the edit-basis rule behind it; Read/Write/Edit are deliberately excluded), compresses via `libs/local_compress_lib.py` (found automatically in `libs/` under the repo root) if output exceeds a threshold (with two exceptions: `local-compress` tools that already compress server-side aren't re-compressed, and a multi-entry `compact_find` result is left untouched so `/my-resume` can count its entries — see [Skills and hooks](docs/skills-and-hooks.md)), fails open (leaves output untouched) if LM Studio is unreachable or the import path is somehow wrong.
