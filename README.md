# ClaudeRunway

Local-compute token savings for Claude Code.

Two independent pieces, both built on the same idea: push work onto local compute (a local vector DB, a local LLM) instead of Claude's own context, so Claude only pays tokens for a distilled result rather than raw data.

1. **Qdrant codebase memory** — per-project semantic memory over code/docs, so Claude can retrieve relevant chunks instead of grepping and reading whole files, and persist distilled findings across sessions.
2. **Local compression (LM Studio)** — a local model summarizes large, mechanical content (logs, build output, big diffs) server-side before anything reaches Claude's context.

Each piece works independently — you don't need LM Studio to use the Qdrant memory, or vice versa.

## Known limitations

- Claude Code doesn't render MCP progress notifications visibly in the UI, though `index_repo`/`sync_repo` still report progress internally to avoid call timeouts on large repos.
- `codebase-indexer` and the `qdrant-find`/`qdrant-store` server are independent MCP servers that both need to agree on `QDRANT_URL`/`COLLECTION_NAME`/`EMBEDDING_MODEL`. `setup_project.py init` writes the same value into every block; a hand edit has to change each one.
- **A hand-authored or copied `.mcp.json` never gets issue upstream #221's `HF_HUB_OFFLINE` fastembed-cache fix** unless `setup_project.py init` (or `/my-setup-clauderunway`) is run against that project on THIS machine. `HF_HUB_OFFLINE` absent or blank keeps the slow huggingface.co round-trip on every `qdrant` server start (can surface as `qdrant (CONNECT_TIMEOUT)`); a `"1"` copied from another machine is worse, because this machine's cache may be cold and the server then fails to start at all. `upgrade` only fixes the fully-absent case, and `init`'s warm-up can fail (it then leaves the value blank and says to re-run), so check its output. Re-run `init` with your original flags re-passed (`EMBEDDING_MODEL` is the one value it preserves on its own). `/my-setup-clauderunway` refuses and points to the raw CLI when a real `QDRANT_API_KEY` is configured. Full mechanism: [Installation](docs/installation.md) and [Prerequisites](docs/prerequisites.md).
- Compression is lossy by nature — don't use the compress tools on source code you intend to edit, or on output you need verbatim (something to parse, a diff to apply, an exact string to grep for next). `compress_text` only saves tokens for content you already legitimately hold (e.g. your own draft); for files and commands use `compress_file`/`compress_command_output`, which read the source server-side.
- **The savings tracker (`/my-savings`) is a heuristic estimate, not a benchmark.** It uses a chars÷3.5 token approximation and estimates the counterfactual online rather than measuring it via a controlled A/B run (that's what `EVALUATION.md`'s tracks are for — see Track D). Treat its numbers as directional.
- **`CLAUDE_RUNWAY_TRACK_SAVINGS` needs setting in two places, not one** (`.mcp.json` for the MCP server, a shell export for the hooks, which have no `env` field). See [Environment variables](docs/environment-variables.md) and [Savings tracker](docs/savings-tracker.md).
- `focus` on `compress_file`/`compress_command_output`/`fetch_url` handles positional asks ("the lead section," "the first N lines") automatically, with two residual limits: the heading-detection heuristic only helps for content with clear heading structure (plain text such as a log falls back to a fixed ~4000-char guess), and `_looks_positional` is a strict whole-phrase match against a fixed list, so a positional phrasing outside it falls through to the position-aware classifier, which isn't fully reliable on its own. See `libs/local_compress_lib.py`'s docstrings.
- **The pipx/`uv tool install` alternative only supports those two install methods, not a bare `pip install`/`pip install --user`.** `claude-runway-setup init` derives `mcp-server-qdrant`'s path as a sibling of `sys.executable`, which holds for pipx and `uv tool install` venvs but not for a bare `pip install --user`, where console scripts can land elsewhere (e.g. `~/.local/bin`).
- **The shared `memory-bank` collection locks in whichever `EMBEDDING_MODEL` created it first** — every project's memory-bank server writes into the SAME collection and Qdrant's named-vector schema is fixed at creation. A project with a different model gets a clear mismatch error, but every project sharing the collection must agree on one value.
- **Changing `EMBEDDING_MODEL` after a collection has data requires manually dropping the collection (directly in Qdrant) and re-indexing** — old and new vectors aren't compatible. Change it deliberately with `init --embedding-model <model>` (which warns; a plain `init` re-run never changes it). `index_repo(reset=True)` cannot do the rebuild itself: it always does a filtered delete that preserves `metadata.source == "memory-bank"` points. If you call `sync_repo` against a dropped collection it returns an explicit error; follow it with `index_repo`.
- **A server-side "auto mode classifier" — separate from anything in `.claude/settings.json` — can block `/my-gh-autowork`'s orchestrator `Agent` call outright** (upstream #195), contradicting the skill's "Zero required human touchpoints" claim in some environments. Confirmed live on 2026-09-19: rejected before the subagent ran a tool call, and a follow-up self-correction via `.claude/settings.json` was separately blocked as `[Self-Modification]`. **Confirmed workaround, causation NOT confirmed:** adding the narrow `Bash(git fetch *)`/`Bash(git push *)`/`Bash(gh pr *)`/`Bash(gh api *)` rules let the identical call succeed on retry. **Never broaden this to a wildcard like `Bash(git:*)`/`Bash(gh:*)`/`Bash(uv:*)`** — each is an arbitrary-command-execution bypass (`git -c alias.x='!<shell command>' x` runs arbitrary shell via git's alias mechanism; `uv run <script>` executes arbitrary code by design). **Narrow is not the same as safe**: even the confirmed rules still permit code execution through legitimate flags (e.g. `git fetch --upload-pack=<cmd>`). See [Installation](docs/installation.md)'s "If you plan to run `/my-gh-autowork`" paragraph.
- **`sync_repo`/`index_repo`/`ingest_to_qdrant.py` retry on a dropped Qdrant connection** (`libs/qdrant_retry.py`). On macOS, Docker Desktop's `vpnkit` can silently close an idle pooled connection while the local embedding model loads, surfacing as `httpx.RemoteProtocolError`/`ConnectError` ([moby/vpnkit#414](https://github.com/moby/vpnkit/issues/414), [docker/for-mac#5857](https://github.com/docker/for-mac/issues/5857)); no Qdrant-side config helps. Raising Docker Desktop's `vpnKitMaxPortIdleTime` (default 300s, `0` disables culling) only reduces how often it happens.
- **LM Studio serves a limited number of requests in parallel (default 4) and queues the rest**, so heavy concurrency (parallel subagents, `/my-gh-autowork`) can push a compression request past the 60s timeout, and that output then reaches Claude uncompressed. It is reported as a timeout, not an outage (upstream #368). See [LM Studio concurrency and the timeout](docs/environment-variables.md#lm-studio-concurrency-and-the-timeout).
