# Savings tracker

An opt-in, off-by-default feature that reports how much local compression (`compress_file`, `compress_command_output`, `fetch_url`) shrank content: the exact characters before, the characters after, and the percent reduction. It surfaces them automatically at session end plus on demand via `/my-savings`.

**Important framing — this is an observation, not a benchmark.** `EVALUATION.md` measures savings rigorously: run a task with the tools, run it again without, diff the two (a controlled A/B). This tracker can't do that — there's no baseline run in a live session. Instead it observes the counterfactual online: `characters before (the raw content that was compressed)` against `characters after (the compressed result actually used)`. Only local-compression events are credited this way, because the tool holds both sides of that comparison directly — it read the raw content and produced the compressed result, so there's nothing to guess. `qdrant-find` activity is intentionally **never** credited as "savings," because its counterfactual (what Grep+Read would have cost instead) isn't observable — the same gap noted under [Skills and hooks](skills-and-hooks.md) for qdrant-find-vs-Grep. Labeling a guess as a measurement would undermine trust in the one number here that IS directly observed. See `EVALUATION.md`'s "Track D" section for the full distinction.

**Characters, not tokens (#438).** Every newly recorded compression figure is an exact character count, so it needs no model or credential and doesn't change with the model. History from before schema v7 is the exception: rows from before schema v6, and v6 rows that held token estimates its character columns didn't cover (a stale MCP server's token-only footers), were reconstructed as tokens × 3.5 and are approximate (see below), or have no size at all. The tracker used to show estimated tokens (chars ÷ 3.5), but a token count depends on the model's vocabulary, which isn't public, so that conversion was a uniform guess that measurement put about 29% low (see #437). The percent reduction is unchanged by the switch: the same ratio was applied to both sides, so it is identical in characters and in estimated tokens. The token figures that remain are of two kinds: the opt-in transcript usage below is real (measured from the session), while the fixed per-turn tool-schema overhead is still an estimate (tracked separately in #439). And because tool schemas ride in the request's cached prefix, the fixed per-turn overhead the `local-compress` server's tools add is reported once, separately, as an annotation — never subtracted from the headline savings number, since doing that would overstate the real tax by roughly 10x on any session past its first turn (cache reads cost far less than the initial cache write). Run `python tools/report_tool_counts.py` for the current live tool count and schema-token estimate rather than trusting a hand-typed number here — this server's tool count has already grown more than once since this doc was written, which is exactly the class of drift that command exists to prevent (see `EVALUATION.md`'s Step A4/B4).

**Enabling it:**

1. In `.mcp.json`'s `local-compress` server env block, set `CLAUDE_RUNWAY_TRACK_SAVINGS` to `1` (accepted values: `1`, `true`, or `yes`, case-insensitive and whitespace-trimmed — anything else, including unset, is treated as off).
2. **Also export `CLAUDE_RUNWAY_TRACK_SAVINGS=1` at the shell level** (e.g. in `~/.zshrc`/`~/.bashrc`, wherever `claude` gets launched from). Both steps are genuinely required, for two different reasons: an MCP server subprocess does inherit your full shell environment (see [Environment variables](environment-variables.md)'s "Why two places" section — not the narrow allowlist this doc used to claim), but only for a key genuinely *absent* from `.mcp.json`'s own `env` block — and `templates/mcp.json.template`/`tools/setup_project.py` always declare `CLAUDE_RUNWAY_TRACK_SAVINGS` explicitly (blank if disabled), so for this toolkit's own generated configs, step 1's explicit entry is unconditionally what the MCP server's own credited tools (`compress_file`/`compress_command_output`/`fetch_url`) actually read — there's no inheritance fallback in practice here. Hook entries in `.claude/settings.json`, by contrast, have no `env` field of their own at all — so they inherit the *entire* parent environment unfiltered, which is exactly what step 2 supplies. Skip step 1 and the MCP server's own credited tools don't see the setting (this toolkit's generated config leaves the key blank rather than omitting it); skip step 2 and `hooks/compress_output.py`/`hooks/session_end_savings.py` don't either — either gap produces silently incomplete tracking, not an error. This is the same rule that applies to `CLAUDE_RUNWAY_LMSTUDIO_URL`/`CLAUDE_RUNWAY_LMSTUDIO_MODEL` for these same hook scripts. `CLAUDE_RUNWAY_COMPRESS_THRESHOLD_CHARS` is the exception, not a fourth example of it — `compress_output.py` is its only reader, so it's shell-only; an `.mcp.json` copy is inert. See [Environment variables](environment-variables.md) for the full list and the reason they share a `CLAUDE_RUNWAY_` prefix.
3. Merge the extended `PostToolUse` matcher (now includes `mcp__local-compress__.*` and a vetted GitHub allowlist) and the new `SessionEnd` hook block from `templates/settings.json.template` into `.claude/settings.json`.
4. Install the skill: `claude-runway-setup init --install-skills` (or `python tools/setup_project.py init --install-skills` from a clone) installs/updates `my-savings` along with every other product skill (issue [#14](https://github.com/Donelle/claude-runway/issues/14)) — equivalent manual copy: `mkdir -p ~/.claude/skills/my-savings && cp skills/my-savings/SKILL.md ~/.claude/skills/my-savings/SKILL.md`.

**Where the data lives:** a single, central SQLite database — `~/.claude/claude-runway/savings.db` by default, one row per session, tagged by project. It's central (not per-repo) on purpose: the cross-project comparison in `/my-savings detail` needs to query across all your projects at once. Override the location with `CLAUDE_RUNWAY_SAVINGS_DB` (an absolute path) in **both** `.mcp.json` and your shell export if you ever change it from the default — same coordination requirement as the other dual-config variables (see [Environment variables](environment-variables.md#keeping-them-in-sync)). The default needs no such coordination since every script derives it identically. Storage goes through a small function-based interface in `libs/savings_ledger.py`, so SQLite (the current backend) can be swapped later without touching any of its callers.

**Sessions that crash or never end cleanly (#306):** a session's events are kept in a transient per-session ledger (`<session_id>.jsonl` in the `sessions` directory next to the database) and only rolled into `savings.db` by the `SessionEnd` hook. A session that crashes, is force-killed, or otherwise never fires `SessionEnd` used to leave that ledger behind for good, and its savings never showed up in `/my-savings`. Now every `SessionEnd` (with tracking on) also recovers other sessions' leftover ledgers: any ledger not written to for longer than `CLAUDE_RUNWAY_SESSION_MARKER_TTL_HOURS` (default 168 hours, the same setting that expires session markers) is rolled up and deleted. The recovered row uses the project recorded on its events and the ledger's last-write time as its end time, so trend views place it in the week it ran. Recovery only happens when some later session ends cleanly with tracking on, and a session idle for longer than that setting looks the same as a dead one. That is harmless: if a recovered session (or any session) is resumed under the same id and ends again, the new events are added to its existing row rather than replacing it, and each event is counted once. Before this change a resumed session's second clean end replaced the row, keeping only its last run.

**Main session vs. subagent savings (#365):** a tool call made inside a subagent fires the same hooks and reports the *parent's* `session_id`, so before this a subagent's savings were indistinguishable from the main session's. The hook now reads the payload's `agent_id` and `agent_type` and writes them onto the event (omitted entirely when absent, so main-session events keep their old shape). At `SessionEnd` the session is also rolled up per agent into the `session_agents` table (schema v5): one row per `(is_subagent, agent_type)` with the same counters as `session_tools` (events, credited events, characters before/after/saved), so a stored record shows whether the saving came from the main session or from a subagent of a given type. Three things worth knowing:
- **A subagent is detected by `agent_id`, never by `agent_type`.** Per the hooks reference, `agent_type` is also present on the *main* thread when the session was started with `claude --agent <name>`; that session's events are filed as main-session (`is_subagent = 0`) with the type kept as a label.
- **The raw `agent_id` is not stored in SQLite**, only in the transient per-session ledger that is deleted at rollup. One row per spawned subagent would grow without bound for little value; type plus the subagent flag answers "main or subagent, and which kind".
- **Sessions finalized before schema v5 have no per-agent rows** — the information was never recorded, so nothing is backfilled. `/my-savings detail` only shows the block when a subagent earned a positive saving this session (a subagent whose only activity was uncredited, e.g. `fetch_url`, or saved nothing, is left out). The JSON/CSV outputs don't include the split yet.

Query it directly, for example `SELECT agent_type, SUM(saved_chars) FROM session_agents WHERE is_subagent = 1 GROUP BY agent_type;`.

**Exact character counts and the tool-call id (#437, schema v6; the only size figures since #438, schema v7):** each compression event records `raw_chars` and `out_chars` (the content before and after compression) and `saved_chars` (clamped at 0, and 0 for uncredited events). The MCP savings footer carries `raw_chars`/`out_chars` and the hook computes them for the other paths. The event also gets the `PostToolUse` payload's `tool_use_id` (left out when absent), so a later change can join an event to its transcript turn and model. At `SessionEnd`, and in orphan recovery, the character fields roll up into `raw_chars_sum`, `out_chars_sum` and `saved_chars` on `session_tools` and `session_agents`, and `raw_chars_sum`, `out_chars_sum` and `credited_saved_chars` on `sessions`.
- **Schema v7 dropped the estimated-token columns (#438):** `credited_saved_tokens`, `raw_tokens_sum` and `out_tokens_sum` on `sessions`, and `saved_tokens`, `raw_tokens_sum` and `out_tokens_sum` on `session_tools` and `session_agents`. New events no longer write the token fields, and the MCP footer no longer carries them. The `actual_*_tokens` columns (real transcript usage) stay, and so does `overhead_tokens` (the tool-schema overhead, which is still an estimate, #439). The migration rebuilds the three tables rather than using `ALTER TABLE ... DROP COLUMN`, which needs SQLite 3.35+. It also re-derives each row's saving as `max(0, before − after)` where both sizes are recorded (v6 stored a sum of per-event clamped savings, see below), keeping the backfilled figure only for rows with no recorded size. A v6 row can also hold token data its character columns don't cover (a savings footer from an MCP server that hadn't been restarted after #437 carried only token estimates, and the hook recorded it); before the token columns are dropped, such a row is reconstructed as tokens × 3.5 where the tokens exceed the characters by more than rounding slack, the same approximation the v6 backfill used for older rows. A row whose characters already cover its tokens keeps them as recorded.
- **Rows written before schema v6 are backfilled as tokens × 3.5**, because that is exactly how they were produced, rounded to a whole number. Each event's token figure was itself rounded before it was summed, so a backfilled row carries a little rounding error; treat it as approximate, not exact. Where a row's before or after token sum is 0 (unknown, from the older migrations), the matching character column is left at 0 (unknown) rather than derived from something else. The saved figure is always known, so it is always backfilled. The token columns were dropped after that backfill, so the backfilled characters are all that remains of those rows.
- **A 0 in a character column means "unknown" as well as zero.** An event logged by an older hook, or by an MCP server that hasn't been restarted since the upgrade, has no character fields and contributes nothing to the sums. A savings footer from an MCP server that predates #437 carries only token estimates; the hook still strips it but records nothing, since there is no exact size to record.
- **Sessions with no recorded size are left out, and counted.** A row with credited events but no before/after (from before schema v6) is not folded into the all-time, per-project or trend totals, because zeros mixed with exact rows would make a partial total look complete. The simple, detail and trend views say how many sessions were left out (`unsized_sessions` in JSON/CSV). `/my-savings` shows "n/a" instead of a percentage when nothing has a recorded size. The JSON and CSV exports carry a `reduction_percent` at every level (session, project, tool, per-project rows; empty/null when there is no recorded before size).
- **A resumed pre-v6 session stays unsized.** If a session whose stored row has credited events but no recorded size is resumed and ends again, its new events add to its event counts only; its character figures and backfilled saving are left as they were, so the row never looks fully sized while covering only part of the session.
- **The saving is derived, never summed.** Each event's saving is clamped at 0 on its own, so adding them up can exceed `before − after` (events 100→150 and 100→10 sum to 90, but 200→160 saves 40). Every stored and displayed saving is therefore `max(0, before − after)` of its own totals, and a resumed session's saving is re-derived from the summed totals. The per-event `saved_chars` in the transient ledger stays as logged.
- **Only events with a recorded size are counted.** A credited event with no valid `raw_chars`/`out_chars` (one logged before #437, or corrupt) is left out of the event counts too, so "N events" and the reduction beside it always describe the same set.
- **`tool_use_id` lives only in the transient per-session ledger**, not in SQLite.

**Using it:** `/my-savings` shows a simple view (this session + this project's all-time totals, each as characters before, characters after and percent reduction); `/my-savings detail` adds a per-tool breakdown, a "Main session vs subagents" block (only when a subagent earned a saving this session — see below), a sparkline of recent sessions, and the cross-project comparison; `/my-savings trend [day|week]` shows a bucketed trend over time (defaults to weekly buckets) via the `savings_trend` tool. `fetch_url` calls are always logged but never credited toward the headline number — its honest counterfactual is WebFetch's own already-compressed summary, which isn't something this toolkit observes.

**Real token counts (opt-in):** export `CLAUDE_RUNWAY_PARSE_TRANSCRIPT_TOKENS=1` in your shell (shell-only — no `.mcp.json` counterpart needed, since only `hooks/session_end_savings.py` reads it) to have the `SessionEnd` hook parse the session's transcript JSONL (plus its subagent transcripts, see below) and extract the actual tokens Anthropic processed per turn. When enabled, the savings summary adds a token breakdown table and cache efficiency ratio at the end of each session:

```
Tokens Anthropic processed · claude-runway
  Token type       Count     % of total   Relative cost
  ────────────────────────────────────────────────────────
  Fresh input      1,523          0.1%    1.00×  (full price)
  Cache writes     ~5.0M          4.3%    1.25×  (storage overhead)
  Cache reads    ~110.6M         95.6%    0.10×  (10× cheaper than fresh)
  Output           ~660K          0.6%    5.00×  (most expensive per token)
  ────────────────────────────────────────────────────────
  Total          ~115.6M        100.0%

  Cache efficiency            72×  (reads vs. fresh input — higher is better)
```

The **Relative cost** column shows approximate cost ratios vs. full input price (not exact Anthropic rates — those aren't exposed to hooks). The **cache efficiency ratio** (`cache_read_input_tokens ÷ input_tokens`) is a health indicator for how well skills and `CLAUDE.md` are structured for Anthropic's prompt caching layer: a high ratio (e.g. 72×) means context has stabilised into a cacheable shape and Claude is reusing existing knowledge rather than re-ingesting fresh tokens every turn — a sign of well-crafted skills. A low ratio signals a lot of novel uncached content entering each turn.

**Usage is counted once per assistant turn:** Claude Code writes one transcript line per content block of a turn, each repeating the whole turn's usage, so the parser counts each distinct `message.id` once. **Figures recorded before this fix (#298) are inflated by roughly 1.9x** (every token type, and therefore the totals; the cache efficiency ratio was largely unaffected), and they remain in `savings.db` unchanged. Don't compare actual-token figures across that boundary.

**Subagent usage is included (#364):** the hook payload's `transcript_path` is only the *main* session's transcript. Claude Code writes each subagent's turns to its own file, `<session_id>/subagents/agent-<agent_id>.jsonl`, next to it, so the totals now also add up every `agent-*.jsonl` file there (each parsed on its own, so the per-`message.id` dedup above stays scoped to one file). **Figures recorded before this change exclude all subagent usage** — they under-report sessions that delegate work (`/my-gh-autowork` most of all), which also made the "% of total processed" ratio look better than it was. Don't compare actual-token figures across this boundary either. Known gap: a subagent still running when the session ends, or a resumed session, may be only partially counted. If Claude Code changes the `subagents/` layout, the glob finds nothing and the totals fall back to main-transcript-only rather than failing.

**Note:** this feature parses Claude Code's internal transcript JSONL format, which is undocumented and may change without notice. It is a stopgap until [anthropics/claude-code#52089](https://github.com/anthropics/claude-code/issues/52089) ships real token counts in the `Stop` hook payload directly (tracked in [#164](https://github.com/Donelle/claude-runway/issues/164)).
