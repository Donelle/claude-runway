# Known limitations

Real, confirmed gaps and sharp edges in the current implementation, not a wishlist — worth reading before relying on this toolkit for anything that matters.

- Claude Code doesn't render MCP progress notifications visibly in the UI, though `cb_indexer_index_repo`/`cb_indexer_sync_repo` still report progress internally to avoid call timeouts on large repos.
- `codebase-indexer` serves both indexing and `cb_indexer_find_repo`/`cb_indexer_store_repo`, so one block decides `QDRANT_URL`/`COLLECTION_NAME`/`EMBEDDING_MODEL` for the project collection. The `compact` block does not carry `COLLECTION_NAME`/`EMBEDDING_MODEL` (its server reads neither); `QDRANT_URL` is the one value both blocks use. `memory-bank`'s `EMBEDDING_MODEL` is deliberately separate (see below).
- Compression is lossy by nature — don't use the compress tools on source code you intend to edit, or on output you need verbatim (something to parse, a diff to apply, an exact string to grep for next). `compress_text` only saves tokens for content you already legitimately hold (e.g. your own draft); for files and commands use `compress_file`/`compress_command_output`, which read the source server-side.
- **The savings tracker (`/cr-savings`) is an online observation, not a benchmark.** It reports exact characters before and after compression and the percent reduction (exact for newly recorded history; rows from before schema v6, and v6 rows rebuilt from token estimates, are approximate or left out), but it observes the counterfactual online rather than measuring it via a controlled A/B run (that's what `EVALUATION.md`'s tracks are for — see Track D). The only token figure is the opt-in per-model one, which is derived (characters saved ÷ that session's own observed chars-per-token, counted once per request that carried the result), labelled as derived, and still not a measurement. Treat what the content would have cost in tokens as unknown beyond that.
- **`CLAUDE_RUNWAY_TRACK_SAVINGS` needs setting in two places, not one** (`.mcp.json` for the MCP server, a shell export for the hooks, which have no `env` field). See [Environment variables](environment-variables.md) and [Savings tracker](savings-tracker.md).
- `focus` on `compress_file`/`compress_command_output`/`fetch_url` handles positional asks ("the lead section," "the first N lines") automatically, with two residual limits: the heading-detection heuristic only helps for content with clear heading structure (plain text such as a log falls back to a fixed ~4000-char guess), and `_looks_positional` is a strict whole-phrase match against a fixed list, so a positional phrasing outside it falls through to the position-aware classifier, which isn't fully reliable on its own. See `libs/local_compress_lib.py`'s docstrings.
- **Chunks are cut to the embedding model's token window, and every file is indexed in full with no cap.** The model embeds only the first N tokens of a text (read from the loaded model; for the default model that is 128 or 256 depending on the FastEmbed version and model snapshot installed, which is why it is read rather than assumed), so the indexer cuts each chunk to fit and reads `EMBEDDING_MODEL`'s own limit rather than assuming one. The cost lands on the caller: chunk count is several times what line-based chunking produced, indexing is slower, collections are bigger, and a minified bundle or data dump can become thousands of chunks (a run of non-whitespace longer than the tokenizer's per-word limit is one unknown token, so such a chunk can be long in characters). There is deliberately no per-file chunk cap and no skip threshold. `cb_indexer_index_repo`/`cb_indexer_sync_repo` report a running count while hashing, then progress per file, and name the files that produced the most chunks, `ingest_to_qdrant.py` prints each file's count, and `cb_indexer_preview_index` shows it beforehand; exclude files you do not need searched with `INDEX_EXCLUDE_DIRS`/`INDEX_INCLUDE_EXTENSIONS`. `overlap` is now in tokens, `chunk_lines` is accepted but ignored, and chunk metadata is `file_path` + `line_number` + `char_range` (points indexed earlier keep `line_range` until re-indexed; readers accept both). If the window cannot be read from the model, indexing stops with an error instead of guessing. See "How files are chunked" in [Installation](installation.md).
- **An index built by an older release is rebuilt by the first `cb_indexer_sync_repo` after updating.** The sync manifest is versioned and an old-format one is ignored, so that sync re-chunks and re-embeds every file in one long call (`upgrade` offers to remove the stale manifest). It first reports points in the collection that are not indexer chunks, which can be deleted with a re-indexed file's old chunks, and afterwards removes chunks of files no longer on disk. `cb_indexer_index_repo` writes the manifest too when it starts from a clean slate (`reset=true`, or a collection that was absent or empty), so a `cb_indexer_sync_repo` after it picks up from there; a `force=true` run into a collection that already holds points writes none, and neither does a run into any collection other than this project's own (the manifest is one file per checkout and does not record which collection it describes). `ingest_to_qdrant.py` writes none unless you pass `--write-manifest`: the CLI reads its connection settings from the shell, not `.mcp.json`, so it cannot tell which collection `cb_indexer_sync_repo` uses for this checkout, and the flag is you saying that `--collection` (on `--qdrant-url`) is that one. With it the CLI follows the same rules as `cb_indexer_index_repo` (written only with `--reset` or into a collection that was absent or empty, never on `--dry-run` or after a failed run, old manifest removed before anything is deleted or stored); without it the first `cb_indexer_sync_repo` after a CLI index re-embeds every file a second time. A file that is still on disk but outside the rebuild's scope (a different `scope`, extensions, excluded directories or gitignore setting) keeps its old chunks and is recorded in the manifest as kept, apart from the file hashes. Every later `cb_indexer_sync_repo` checks whether such a file has been deleted and removes its chunks if so, and re-indexes it once a scan includes it; a file whose existence cannot be checked is left alone.
- **`cb_indexer_index_repo`, `cb_indexer_sync_repo`, `cb_indexer_store_repo` and `ingest_to_qdrant.py` only write into a collection the codebase-indexer created.** Each collection they create is marked in its Qdrant metadata, and an existing collection without the mark is refused, whatever `reset`/`force` say and whatever it is called: the memory bank, a compact collection, anything else. A code collection indexed before the mark existed is adopted (marked, then used) when it holds at least one indexed file chunk (`metadata.file_path`) and no memory-bank or compact points. An EMPTY unmarked collection is not recognised and is refused: drop it in Qdrant, or pick another `COLLECTION_NAME`. The check fails closed, so a Qdrant error while reading the collection's metadata refuses the run too.
- **Only one `cb_indexer_sync_repo`, `cb_indexer_index_repo` into this project's own collection or CLI `--write-manifest` run at a time per checkout.** Each holds a lock on `.qdrant_index_manifest.json.lock` from before it reads the manifest or counts the collection to its final save, and a second run on the same checkout (a second Claude Code session syncing at start, say) is refused at once with an error instead of waiting; run it again once the first has finished. Without the lock, overlapping runs could leave a file's old chunks in the collection while the manifest recorded its new hash, so later syncs would skip it. The lock file stays in the repo root between runs: gitignore it with the manifest. On a filesystem without OS file locks (some network mounts) runs proceed unlocked, as before. See "One manifest user at a time per checkout" in [Installation](installation.md).
- **`cb_indexer_find_repo` returns 10 hits unless you pass `limit`.** Repetitive content (generated clients, JSON fixtures, lock files) can fill the top 10 with near-duplicates and push the chunk you want past it: raise `limit`, narrow the query, or fall back to Grep on a local checkout or `cb_indexer_find_in_collection` with a higher `limit`. A hit with `line_range` in its metadata comes from an index that predates token-window chunking, where most of each chunk could not be matched at all, so a miss there is not proof the code is absent.
- **The shared `memory-bank` collection locks in whichever `EMBEDDING_MODEL` created it first** — every project's memory-bank server writes into the SAME collection and Qdrant's named-vector schema is fixed at creation. A project with a different model gets a clear mismatch error, but every project sharing the collection must agree on one value. That value is the `memory-bank` block's own `EMBEDDING_MODEL`, set independently of the code-index model: `init --embedding-model` never touches it, and `init --memory-bank-embedding-model` changes it (with a warning).
- **Changing `EMBEDDING_MODEL` after a collection has data requires manually dropping the collection (directly in Qdrant) and re-indexing** — old and new vectors aren't compatible. Change it deliberately with `init --embedding-model <model>` (which warns; a plain `init` re-run never changes it). `cb_indexer_index_repo(reset=True)` cannot do the rebuild itself: it always does a filtered delete that preserves `metadata.source == "memory-bank"` points. If you call `cb_indexer_sync_repo` against a dropped collection it returns an explicit error; follow it with `cb_indexer_index_repo`.
- **A server-side "auto mode classifier" — separate from anything in `.claude/settings.json` — can block `/cr-gh-autowork`'s orchestrator `Agent` call outright**, contradicting the skill's "Zero required human touchpoints" claim in some environments. The denial seen in practice is the classifier's built-in "Merge Without Review" rule (merging before human approval): the subagent prompt ends in `gh pr merge --squash`, and Copilot's automated review is not human approval to the classifier, so the `Agent` call is rejected before the subagent runs a single tool call. **The classifier runs after the permission rules, so no `Bash(...)` entry in `permissions.allow` matches this denial and none can clear it.** The lever is an `autoMode.allow` entry (prose, not a pattern) in `~/.claude/settings.json`, user scope only: Claude Code ignores `autoMode` in `.claude/settings.json` and `.claude/settings.local.json`. List the literal `"$defaults"` first, because an `allow` list without it replaces the built-in rules instead of adding to them. A suggested entry: `"The user has authorized /cr-gh-autowork to spawn autowork-ticket subagents that work and squash-merge pull requests on Donelle/claude-runway with gh pr merge. Merging is gated by the repository's Copilot review_on_push ruleset and required status checks, which stand in for human approval; this is deliberate, not a review bypass."` Confirm what is in effect with `claude auto-mode config`; `/auto-mode-setup` drafts `environment` entries. For a one-off, stating the intent in a message and retrying has worked (the identical call succeeded on retry right after a denial). **Claude cannot make this edit for you:** the built-in Self-Modification block stops an agent from adding or widening permissions in its own config (a self-correction through `.claude/settings.json` was blocked that way), so you make the change. The `Bash(...)` rules are a separate layer: they decide whether the subagent's own `git`/`gh` commands run without a prompt (`/cr-gh-autowork`'s preflight checks for them). An earlier workaround, adding the narrow `Bash(git fetch *)`/`Bash(git push *)`/`Bash(gh pr *)`/`Bash(gh api *)` rules, was followed by a successful retry, but **causation was never confirmed**, and since the classifier runs after the permission rules the retry itself is the likelier explanation. **Never broaden those rules to a wildcard like `Bash(git:*)`/`Bash(gh:*)`/`Bash(uv:*)`** — each is an arbitrary-command-execution bypass (`git -c alias.x='!<shell command>' x` runs arbitrary shell via git's alias mechanism; `uv run <script>` executes arbitrary code by design). **Narrow is not the same as safe**: even narrow rules still permit code execution through legitimate flags (e.g. `git fetch --upload-pack=<cmd>`). See [Installation](installation.md)'s "If you plan to run `/cr-gh-autowork`" paragraph.
- **`cb_indexer_sync_repo`/`cb_indexer_index_repo`/`ingest_to_qdrant.py` retry on a dropped Qdrant connection** (`libs/qdrant_retry.py`). On macOS, Docker Desktop's `vpnkit` can silently close an idle pooled connection while the local embedding model loads, surfacing as `httpx.RemoteProtocolError`/`ConnectError`; no Qdrant-side config helps. Raising Docker Desktop's `vpnKitMaxPortIdleTime` (default 300s, `0` disables culling) only reduces how often it happens.
- **LM Studio serves a limited number of requests in parallel (default 4) and queues the rest**, so heavy concurrency (parallel subagents, `/cr-gh-autowork`) can push a compression request past the 60s timeout, and that output then reaches Claude uncompressed. It is reported as a timeout, not an outage. See [LM Studio concurrency and the timeout](environment-variables.md#lm-studio-concurrency-and-the-timeout).
