# Environment variables

**Any variable read by _both_ halves of the toolkit must be set in _two_ places, with _identical_ values: `.mcp.json`'s `env` block *and* an export at the OS/shell level.** Setting only one side does not raise an error, and won't even reliably fail silently either — an MCP server subprocess *does* inherit a shell export when `claude` happens to be launched from a shell that already ran it (see "Why two places" below), but ONLY when that variable's key is genuinely *absent* from the server's own `env` block; a key that's present there, even set to `""`, always overrides/masks the inherited value rather than falling through to it. This toolkit's own shipped templates (`templates/mcp.json.template`, `tools/setup_project.py`) always declare the specific `CLAUDE_RUNWAY_*` variables that actually need coordinating across both halves (`LMSTUDIO_URL`/`LMSTUDIO_MODEL`/`TRACK_SAVINGS`) explicitly in the MCP server's `env` block (blank if disabled) — so for those variables specifically, that inheritance path never actually gets a chance to apply. `SAVINGS_DB` is the exception among the coordinated ones: `init` writes it into the `analytics` block only when overridden, so with the default it is absent there and inherits. This doesn't extend to every `CLAUDE_RUNWAY_*` name: `CLAUDE_RUNWAY_CACHE_DB` (read by both the `codebase-indexer` MCP server AND the `redirect_webfetch_to_fetch_url.py` hook — shell export is the override channel since hooks can't read `.mcp.json`), `CLAUDE_RUNWAY_SESSION_MARKER_TTL_HOURS` (read by both the `record_session_id.py` hook AND the `local-compress` MCP server — same: shell export only, left undeclared in `.mcp.json` so the server inherits it) and `CLAUDE_RUNWAY_COMPRESS_THRESHOLD_CHARS`/`CLAUDE_RUNWAY_EXTRA_EXACT_PATTERNS`/`CLAUDE_RUNWAY_WEBFETCH_FAILED_URL_TTL` (hook-only) aren't part of the two-places coordination rule — see the `Set it in` column below for which variables actually need both places. This is the single most common misconfiguration here. The `Set it in` column below is authoritative; don't assume every variable needs both.

## LM Studio concurrency and the timeout

LM Studio runs up to **4 requests in parallel** by default (the per-model **Max Concurrent Predictions** load setting) and **queues the rest**. A burst of compressions — parallel subagents, `/my-gh-autowork`, several tool calls compressed at once — can therefore leave a request waiting in LM Studio's queue past `CLAUDE_RUNWAY_LMSTUDIO_TIMEOUT_SECONDS`. The output then reaches Claude uncompressed (the hook fails open) and the failure is reported as a **timeout**, not an outage:

| What happened | What you see |
| --- | --- |
| A request timed out (LM Studio busy or unreachable) | `Error: LM Studio request timed out after Ns (...) -- LM Studio may be busy with other requests or unreachable`; with `preserve_sections`, if *every* request timed out, a `[LM Studio timed out on every request ...]` prefix |
| LM Studio answered HTTP 400 and refused the request (most often a chunk that does not fit the loaded model's context window) | `Error: LM Studio rejected the request (...) (LM Studio said: <server message, truncated>) -- most often the chunk is too large for the loaded model's context window: retry with a smaller chunk_chars, or load the model with a larger context length in LM Studio`; with `preserve_sections`, if *every* request was rejected, a `[LM Studio rejected every request ...]` prefix |
| Connection refused, model not found, or any other failure | `Error: LM Studio request failed (...) -- check it's still running`; with `preserve_sections`, `[LM Studio appears unreachable ...]` |

To reduce timeouts, in order of preference:

1. **Raise Max Concurrent Predictions** in LM Studio (model loader → *Show advanced settings*). More requests run in parallel instead of queueing; the cost is memory.
2. **Raise `CLAUDE_RUNWAY_LMSTUDIO_TIMEOUT_SECONDS`.** Still bounded, but it loosens the limit that stops a genuinely hung server from stalling a hook for ~30 minutes.

The limit belongs to LM Studio, not claude-runway, so there is no client-side concurrency cap to configure. Verified 2026-10-03 on the MLX engine: 4 concurrent requests finished in the time of 1, and with 6, two waited for a free slot. LM Studio's [Parallel Requests](https://lmstudio.ai/docs/app/advanced/parallel-requests) page documents the default of 4 and the queueing, though it still lists MLX support as "coming soon".

### A chunk that overflows the model's context window

The server is running in this case, so the advice is not "check it's still running". LM Studio rejects a request whose prompt does not fit the context length the model was loaded with (the default loaded length is small for some models) with HTTP 400, and the compression tools report that with the server's own message (truncated, with anything credential-shaped redacted). Token-dense text, such as `ls -lR` output or long lists of paths and numbers, tokenizes far denser than source code, so a chunk of the default `chunk_chars` (12,000 characters) can overflow a small context while the same number of characters of source fits. The character count is not what the server measures.

Two fixes, either is enough:

1. **Pass a smaller `chunk_chars`** to `compress_file`/`compress_command_output`/`fetch_url` (for example `2500`). The cost is more chunks, so more model calls.
2. **Load the model with a larger context length** in LM Studio (model loader → *Context Length*). The cost is memory.

A 400 is not proof of a context overflow, which is why the message says "most often": read the quoted server message to confirm. The hook (`hooks/compress_output.py`) fails open on this error like any other, so the original output reaches Claude uncompressed; it does not pass a `chunk_chars`, so for token-dense output that keeps failing, the fix there is the larger context length.

## Why two places

The two halves of this toolkit configure environment variables through different guarantees, even though both actually inherit the same base channel (the full parent process environment): MCP servers additionally get a per-server `env` block in `.mcp.json` layered on top of that inheritance; hooks have no equivalent override channel at all.

- **MCP servers** (`qdrant`, `local-compress`, `codebase-indexer`, `memory-bank`, `analytics`) run as stdio subprocesses. Verified directly against live processes (`ps eww -p <pid>`): a stdio subprocess actually inherits the **entire parent shell environment** — not the small MCP-spec allowlist this section used to claim — but only for a key that's genuinely *absent* from `.mcp.json`'s own `env` block; a key that's present there, even set to `""`, always overrides/masks whatever the shell would have supplied, rather than merely adding to it. In practice this means relying on inheritance is fragile for a different reason than the old claim implied: `claude` isn't always launched from a shell that ran the export (a GUI launcher, a different profile, a non-interactive shell, another machine), AND this toolkit's own shipped setup (`templates/mcp.json.template`, `tools/setup_project.py`) always pre-declares the specific `CLAUDE_RUNWAY_*` variables that need coordinating across both halves (`LMSTUDIO_URL`/`LMSTUDIO_MODEL`/`TRACK_SAVINGS`) explicitly (blank if disabled) — so for those variables specifically, inheritance never actually gets a chance to apply. (`SAVINGS_DB` is written into the `analytics` block only when overridden.) (Not every `CLAUDE_RUNWAY_*` name is covered by this — `CLAUDE_RUNWAY_CACHE_DB` genuinely isn't declared in the shipped templates, so it could in principle be supplied by inheritance; since `redirect_webfetch_to_fetch_url.py` also reads it now, an override must be a shell export, not a `.mcp.json` entry — see the env var table above.) Set the coordinated ones explicitly in that server's `env` block in `.mcp.json` regardless.
- **Hooks** (`compress_output.py`, `redirect_webfetch_to_fetch_url.py`, `session_end_savings.py`) are plain command hooks. A hook entry in `.claude/settings.json` has **no `env` field at all**, so it inherits the entire parent environment unfiltered. A shell export is the *only* channel that exists for it, and it cannot read `.mcp.json`.

**Security-relevant consequence of the above:** since a stdio MCP server inherits the entire launching shell's environment, this applies to *every stdio-transport* MCP server configured in a project's `.mcp.json` — not just this toolkit's `local-compress`/`codebase-indexer`. (An HTTP/SSE-transport MCP server is a remote service, not a local subprocess Claude Code spawns, so it can't inherit shell environment this way at all.) An unrelated secret merely exported in your shell (an API key, an auth token) is visible to any stdio server in that file; there's no per-server isolation boundary to rely on here.

So the requirements point in opposite directions and neither substitutes for the other. For a variable both halves read: set it only in `.mcp.json` and the hooks never see it — that failure is absolute, since a hook entry has no `env` field at all to read it from. Set it only in the shell and the MCP server *can* still see it — but only if that key is genuinely absent (not merely blank) from the server's own `env` block, AND `claude` happened to be launched from that exact shell. This toolkit's own shipped templates always declare the specific `CLAUDE_RUNWAY_*` variables that need coordinating across both halves, so in practice that inheritance path never actually applies to those — not to every `CLAUDE_RUNWAY_*` name (see the env var table above). A variable only one half reads (see the `Set it in` column above) only needs that half's channel.

## Keeping them in sync

For the variables that do need both copies, nothing enforces that they agree automatically — divergent values are not an error, they just produce split behavior that's confusing to debug:

- Different `CLAUDE_RUNWAY_LMSTUDIO_MODEL` on each side → your hooks compress with a different model than `compress_file`/`fetch_url` do, so quality differs by code path.
- Different `CLAUDE_RUNWAY_SAVINGS_DB` → the savings tracker writes to two separate databases and `/my-savings` reports from only one of them.
- Different `CLAUDE_RUNWAY_TRACK_SAVINGS` → whichever half is set to off just never logs, so the totals silently under-report rather than erroring.

Run `python tools/doctor.py /path/to/target-repo` to check this instead of relying on noticing split behavior by hand — it opens that repo's `.mcp.json`, extracts the env block of each server that reads one of the four vars above (`local-compress` for the two LM Studio values and `CLAUDE_RUNWAY_TRACK_SAVINGS`; `qdrant` for the two LM Studio values, which `compact_store` compresses with; `analytics` for `CLAUDE_RUNWAY_SAVINGS_DB`), and diffs those vars against the live shell environment (so run it from the same shell, or an equivalent one with the same exports, that launches `claude`). Exits 1 and prints the specific divergence if anything disagrees, 0 (with a short "OK" line) otherwise — including when no block has a dual-config value to compare (e.g. a hand-built `.mcp.json` with no `local-compress` server and none of these keys in the `qdrant` or `analytics` block), which is a valid state, not a misconfiguration. See `libs/doctor_lib.py`'s docstring for exactly how each variable's blank-vs-absent/default distinction is resolved, since that differs per variable (mirroring `local_compress_lib.py`/`savings_ledger.py`'s own real resolution rules).

```bash

# export CLAUDE_RUNWAY_SAVINGS_DB="/path/to/savings.db"       # only if overridden; must match the analytics block
export CLAUDE_RUNWAY_COMPRESS_THRESHOLD_CHARS="2000"           # shell only -- no .mcp.json counterpart
export CLAUDE_RUNWAY_LMSTUDIO_TIMEOUT_SECONDS="60"             # shell only, optional -- per-request LM Studio timeout in seconds (bounds a hung LM Studio)
export CLAUDE_RUNWAY_EXTRA_EXACT_PATTERNS="internal-cli;my-hash-tool\b"  # shell only, optional -- adds to (never replaces) the built-in exempt list
```

### Generating the shell side

`scripts/bootstrap.sh` (macOS and Linux, from a clone) writes the shell side for you to `~/.claude/claude-runway/env.sh`, as `export` lines, each with a comment saying what it controls. The script owns that file: it rewrites the whole file on every run and never reads it back, so do not edit it. It takes the four `CLAUDE_RUNWAY_*` values `.mcp.json` declares from the server block that reads each one (the first of `local-compress`, `qdrant`, `analytics`; a literal `REPLACE-WITH-...` placeholder counts as not declared) and sets them as written: a `${NAME}` or `${NAME:-default}` reference in such a value is left for the shell to expand, the same forms Claude Code expands for the MCP server, while any other `$`, `$(...)` or backtick is escaped so a value in a committed `.mcp.json` can never run a command in your shell. It sets `CLAUDE_RUNWAY_DIR` to the checkout the script ran from. Every other value, and the shell-only settings above, is set only when the variable is unset (an ordinary quoted assignment guarded by `${NAME+set}`), so a value you already export in your shell wins and the default applies only when the variable is unset. A changed `.mcp.json` is picked up with `./scripts/bootstrap.sh --env-only`, which skips the install and runs the doctor check afterwards (with the new file loaded for that check, since your running shell has not loaded it yet). Your own overrides and exports go in `~/.claude/claude-runway/env.local.sh`: the last line of `env.sh` loads it if it exists, and the script never reads or writes it. Before replacing `env.sh`, the script checks that the new file parses in bash (and zsh, when installed); if it does not, the old file stays, the script names the `.mcp.json` value at fault and stops, so a file that would break every new terminal is never installed. `env.sh` is created readable only by you and keeps whatever mode you later give it.

The script then offers to add one marked block to your shell profile that loads the file, and writes it only if you answer yes (the default is no; `--update-profile` answers yes without asking, and a piped or non-interactive run prints the block instead of writing it). It only appends, it skips a profile that already mentions the file, and it writes through a symlinked profile to the file it points at. On macOS the profile is `~/.zshrc` for zsh, and for bash the first of `~/.bash_profile`, `~/.bash_login` and `~/.profile` that exists (Terminal opens bash login shells, which do not read `~/.bashrc`). Choosing the profile on Linux is not automated yet: there the script prints the block.

A Claude Code started from the Dock or a desktop app does not read your shell profile, so the hooks would not see these variables; start it from a terminal. `launchctl setenv NAME value` sets one for GUI apps on macOS, and the script does not do that. `claude-runway-doctor` compares `.mcp.json` with the shell it runs in, so it reports OK from a terminal even when a GUI-launched Claude Code lacks them.

Changing either side requires a full restart of Claude Code, not just a new shell: MCP servers read their environment once at startup, and hooks inherit from the already-running `claude` process.

## Renamed in this version

`LMSTUDIO_BASE_URL` → `CLAUDE_RUNWAY_LMSTUDIO_URL`, `LMSTUDIO_MODEL` → `CLAUDE_RUNWAY_LMSTUDIO_MODEL`, `HOOK_COMPRESS_THRESHOLD_CHARS` → `CLAUDE_RUNWAY_COMPRESS_THRESHOLD_CHARS`. **The old names are no longer read at all** — there's deliberately no fallback, so two live name sets can't drift.

The prefix exists precisely *because* these have to live in a global shell profile: an unnamespaced `LMSTUDIO_MODEL` sitting in `~/.zshrc` is easy for another tool to collide with and hard to attribute back to this toolkit.

To make an unmigrated config loud rather than silent, `libs/local_compress_lib.py`'s `stale_env_warning()` detects "old name set, new name missing" and callers surface it — a hard error from the MCP server (checked *before* model auto-detect, so you get the real cause instead of a misleading "multiple models are loaded" message), and stderr plus a note on the fail-open path from the hooks. It stays quiet when both names are set, since the new one wins and the leftover is harmless.
